# Releases

How a version of the modules of this repository is released, and the release protocol of
each version (§ 87c (3) AO: the program, its tests and their results must be
documented). The protocol names results, never amounts or other data of a real business.

## Release process

1. **Code on `19.0`:** all changes merged, version `19.0.x.y.z` in the manifests,
   `readme/HISTORY.md` of every changed module updated, README files regenerated by
   pre-commit.
2. **Checks in a fresh database** (the module `l10n_de_euer`, local docker compose
   setup):
   - `_dev/werkzeuge/test_protocol.sh -d <new database>` runs every test with coverage
     of lines and branches and writes `junit.xml`, `coverage.xml`, `coverage-html/`,
     `test.log` and `summary.md` (tag, commit, Odoo version and image, PostgreSQL
     version, counts and coverage per module and in total; a failed `setUpClass` counts
     for its module). The summary is written by `_dev/werkzeuge/protocol_summary.py`,
     the same as in the workflow `release`, and so is the version of coverage.py
     (7.16.2).
   - The tests run twice, each time in a database of its own: without and with the OCA
     reconciliation modules `account_reconcile_oca`, `account_in_payment` and
     `account_payment_order` (spec 9.9 "Matrix OCA-Abgleich"). The coverage is the
     combined one of both runs; a test counts as skipped only if both runs skipped it.
     The workflow `release` does the same.
   - `pytest` runs the tests without Odoo and without a database (spec 9.9, fast
     feedback): the calculation engine and the tools of the test protocol
     (`pytest.ini`); the engine tests also run inside the protocol above.
   - `pre-commit run --all-files` is clean (also the job `pre-commit` of the CI); every
     `i18n/de.po` is complete.
   - Coverage: at least 95 % of lines and at least 95 % of branches in every module and
     in the project, 100 % of changed code (`codecov.yml`, spec O-06). The protocol
     states both: the coverage of the project and the coverage of the lines and branches
     changed since the previous release (patch coverage).
3. **Private checks** (never in this repository, decision D6): the regression test
   against the previous system with real data (PT-02/PT-03), the second calculation of
   the reference cases (RT-02) and, from E6 on, the ERiC validation (RT-03). They run on
   the commit of the release; their results go into the protocol without amounts.
4. **Data protection review before every push** (spec O-14, RI-10): the working tree and
   every commit that the push publishes (`git log -p` of the range, not only the working
   tree) are scanned with the private list of real names, amounts, dates and document
   numbers; the protocol records the result (number of hits, never the list). Real data
   in the history is removed before the first public push (new root commit or rewritten
   history, released by the maintainer), never only in the working tree.
5. **Liability notice** (spec 1.5, RI-12): a lawyer or an independent tax expert reads
   the notice of `readme/DESCRIPTION.md` and the short notice of the fill-in aid; the
   feedback is worked in. Decision of the maintainer of 22.10.2026: the Alpha 19.0.1.0.0
   is published with the notice reviewed by the maintainer only; the short notice points
   to the warranty exclusion. The review is due before Beta.
6. **Releases by people** (F-11, D7): a form year is set to _verified_ only by the
   release role, never by the person who created its data or by a program; the expected
   values of RT-01 are confirmed in writing by an independent tax expert. The protocol
   records who released what and when. Decision of the maintainer of 22.10.2026: the
   Alpha 19.0.1.0.0 is published without this confirmation and says so in the README
   ("Alpha, not independently checked"); the form years ship as drafts.
7. **Tag:** an annotated tag `19.0.x.y.z` on the commit, created from a clean working
   tree. The workflow `release` runs the tests once more and attaches the test protocol
   (JUnit XML and coverage) to the GitHub release. Run `test_protocol.sh` again on the
   tagged commit: its `summary.md` must show the tag and a clean working tree, otherwise
   it is no release protocol. Started by hand for an existing tag (_Actions → release →
   Run workflow_, input `tag`), the workflow creates the protocol of that tag again with
   the tools of `19.0` and replaces the asset of the release.
8. **Archive:** both test protocols (GitHub release asset and local run) and the private
   results are kept by BM1 for five years.

The development status follows the reference cases: _Alpha_ until RT-01 is confirmed by
an independent tax expert, _Beta_ after the first real statement computed with the
module has been checked by an independent tax expert against receipts and statements of
account (RT-04).
